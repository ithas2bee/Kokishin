# OpenAPI

Kokishin uses ASP.NET Core's built-in OpenAPI support to generate a machine-readable
description of its implemented HTTP API. The document is generated from the
registered endpoints and their response metadata; it is not a separate,
hand-maintained endpoint inventory.

## Access

In Development, run the API and request
[`/openapi/v1.json`](http://localhost:5108/openapi/v1.json). The development launch
profiles use port `5108`. The generated document can be used by API clients,
contract tests, and tools that accept OpenAPI JSON.

OpenAPI is not exposed by default in Production. To intentionally enable it,
set `OpenApi:ExposeInProduction` to `true`, for example with an environment
variable:

```sh
export OpenApi__ExposeInProduction=true
```

The setting defaults to `false` in `appsettings.json`. A production deployment
should enable the document only when its API discovery policy permits public
access; the generated document contains no configuration values.

## Current contract

The API always registers `GET` and `HEAD /health/database`. When authentication
is configured, it also registers authenticated `GET` and `PUT /me/profile`
operations for the caller's own profile and Instructor-only course management
operations:

- `POST /courses` accepts a required `title` and optional `description`; it
  does not accept an owner identifier. The owner is the Instructor account
  resolved from the validated principal. A successful response returns `201`
  with the course ID, owner ID, title, description, and initial `Draft` status.
- `GET /courses` returns the authenticated Instructor's courses as an array of
  course ID, owner ID, title, description, and status. Any client-supplied
  owner identifier is ignored; the owner is derived from the validated
  principal. An Instructor with no courses receives `200` and an empty array.
- `GET /courses/{courseId}` returns the same course fields for a course owned
  by the authenticated Instructor. A missing course or one owned by another
  Instructor returns `404`, without exposing its details.
- `PUT /courses/{courseId}` accepts a required `title` and optional
  `description` for a course owned by the authenticated Instructor. The course
  ID comes from the route, and the owner is derived from the validated
  principal; request properties for ID, owner, or status do not change them.
  A successful response returns `200` with the updated course ID, owner ID,
  title, description, and unchanged status. Validation failures return `400`,
  while a missing or non-owned course returns `404`.
- `PUT /courses/{courseId}/publication-status` accepts `{"status":"Published"}`
  or `{"status":"Draft"}` for a course owned by the authenticated Instructor.
  The only valid transitions are Draft to Published and Published to Draft;
  requesting the current status or an unsupported value returns `400`. A
  missing or non-owned course returns `404`. The response contains the course
  ID, owner ID, title, description, and new status. Changing status does not
  create or modify enrollments and Published does not bypass the active
  enrollment requirement; see [AD-009](decisions/AD-009-course-publication.md)
  and [AD-008](decisions/AD-008-course-enrollment.md).
- `POST /courses/{courseId}/enrollments` accepts a `learnerAccountId` for an
  active Learner account. The active Instructor identity is derived from the
  authenticated principal, and the course must be owned by that Instructor.
  A new enrollment returns `201` with the course ID, learner account ID, and
  `Active` status. Repeating the request for an already active enrollment is
  idempotent and returns `200` without creating another record. An enrollment
  in `Withdrawn` or `Removed` state is explicitly re-enrolled and returns `200`;
  a `Suspended` enrollment returns `409` and remains unchanged. Unknown course
  or learner IDs return `404`; an inactive or non-Learner account returns
  `400`. Anonymous callers receive `401`; non-Instructors and inactive
  Instructors receive `403`; an Instructor who does not own the course receives
  `404`. The request does not accept a caller account ID or role.

Course creation and update validation failures return a `400` Problem Details
response. Anonymous callers receive `401` and Learners receive `403` for all
course management operations, including publication status changes and
enrollment.

The generated document describes the `200` and `503` plain-text health results,
the authenticated profile and course operations, and the `500` error response
(`application/problem+json`) handled by the API exception middleware.

Problem Details responses are generated by the existing ASP.NET Core error
handling. The `400` course-validation and `500` server-error responses are
represented in OpenAPI. A `404` unmatched-route response is not represented as a
fictional API path.

To verify the contract, run `dotnet test Kokishin.sln`. The API integration tests
request the generated document and check the registered endpoint, methods,
response metadata, and environment-specific exposure.
